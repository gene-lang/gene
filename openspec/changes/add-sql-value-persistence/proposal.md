## Why

Gene currently has three SQL extensions (`src/genex/sqlite.nim`, `postgres.nim`, `mysql.nim`) but they only bind scalar `Vk*` kinds; non-scalar values fall back to `$value` string interpolation (`src/genex/sqlite.nim:31-44`, `postgres.nim:33-44`, `mysql.nim:24-37`), which is lossy and not round-trippable. No generic, backend-portable "store any Gene value" layer exists. Prior persistence work (`add-geneclaw-data-storage-tiers`) chose filesystem text `.gene` files; SQL was reserved for app-specific operational tables (`add-llm-chat-storage`). Users who want durable, queryable, transactional storage of arbitrary Gene values across SQLite, MySQL, and PostgreSQL have no portable answer today.

## What Changes

- Add a new capability `sql-value-persistence` with a single canonical, backend-portable logical schema for storing multiple unrelated Gene values, each keyed by a unique string id.
- Define per-backend DDL templates for SQLite, MySQL, and PostgreSQL that materialize the same logical schema.
- **Always-inline root payloads**: every `put` stores its encoded value in a single `inline_payload` column on `gene_values`. v1 deliberately ships no size-based auto-detach of root values — there is no `inline_threshold`, no root-level `blob_sha256`, no root-level routing to a content-addressed sidecar, no `^external_uri` tier. Callers who know a particular sub-field is large declare it explicitly with `^externalize` (next bullet); auto-detection of large leaf strings/bytes is deferred to a future change that can layer onto the same schema without migration.
- **Developer-declared field-level externalization** (the only externalization mechanism in v1): `put` accepts an optional `^externalize [/path …]` array (mirroring the filesystem-serdes selector syntax in `src/gene/serdes.nim:1141-1217`). Each listed sub-tree of the value is encoded into its own row in a content-addressed `gene_blobs` table regardless of size, the parent payload stores a placeholder marker at that path, and a mapping table `gene_value_blobs(value_id, child_path, blob_sha256)` records which child path of which value owns which blob. On read, each externalized child is returned as a `VkLazyDbValue` at its declared path so individually-large fields are not fetched until accessed.
- Use **SHA-256 content addressing** for externalized child blobs, enabling free deduplication across unrelated values that share an identical sub-tree.
- Reuse the existing text serdes wire format (`src/gene/serdes.nim:850+`) as the v1 payload format; reserve an `inline_format` byte on `gene_values` for a future binary format without schema migration.
- **Fast-path `put`**: when no `^externalize` is given, `put` is a single prepared UPSERT against `gene_values` — one round-trip, no read-before-write, no touch of `gene_blobs` or `gene_value_blobs`. When `^externalize` is given the bound is `1 + 2·N + K` round-trips (root upsert + per-child blob and mapping upserts + at most `K ≤ N+1` orphan-cleanup deletes for blobs whose last reference was just removed). No application-side existence checks, no triggers, no per-update ref-count writes on the schema.
- **Seamless blob lifecycle**: when a `^externalize` operation evicts a previously-mapped `blob_sha256`, the same transaction issues `DELETE FROM gene_blobs WHERE sha256 = ? AND NOT EXISTS (SELECT 1 FROM gene_value_blobs WHERE blob_sha256 = ?)`. The check is single-table because v1 has no `gene_values.blob_sha256` column for root payloads. No user-callable `gc_blobs` API; no external DB job.
- **Lazy materialization for externalized children only**: `get` returns the root value fully materialized; each externalized child path inside the returned value is a `VkLazyDbValue` wrapper that fetches and decodes its blob on first content access. The wrapper is type-transparent at the Gene level — `(gene/kind v)` reports the cached original kind via an explicit branch in the `kind()` introspection path; structural access (iteration, indexing, property read, equality, serialization) materializes the wrapper in place. An explicit `(genex/db_store/materialize v)` escape hatch is exposed for callers who need eager resolution.
- Add a Gene API `(import genex/db_store)` exposing `open`, `put`, `get`, `has?`, `delete`, `scan`, `close` on top of any existing SQL connection.
- Define an explicit root-level CRUD contract: every read, write, update, or delete of persisted state must be an intentional `genex/db_store` operation against a store handle and root value id. Nested field access may lazily materialize bytes, but it MUST NOT implicitly write, update, or delete database rows; v1 has no child-path mutation/delete API.
- Confirm the existing `nimble buildext` MySQL target (already landed at `gene.nimble:44` in commit `8d499f5e`) stays green under this proposal; add a CI smoke test that exercises the MySQL driver against the docker-compose service so MySQL is verified at parity with SQLite and Postgres rather than just buildable.
- Document which `Vk*` kinds are persistable (all serdes-supported kinds plus `VkCustom` class hooks) and which are explicitly non-persistable (`VkFunction`, `VkScope`, `VkFrame`, `VkThread`, `VkFuture`, `VkNativeFn`, …) so callers get a deterministic error rather than silent loss.

## Impact

- **Affected specs**: new capability `sql-value-persistence`. No modifications to existing capabilities; orthogonal to filesystem-tier work (`add-geneclaw-data-storage-tiers`) which remains the answer for human-authored config and append-only logs.
- **Affected code**:
  - New: `src/genex/db_store.nim` (Gene-facing layer), shared with existing connection types from `src/genex/{sqlite,postgres,mysql}.nim`.
  - New: `src/genex/db_store/schema.nim` (DDL templates), `src/genex/db_store/codec.nim` (payload encode/decode with `^externalize` child extraction; root encoding never hashes).
  - Modified: `gene.nimble` — MySQL `buildext` target already present (line 44); this proposal adds the CI smoke job that runs the MySQL driver against the docker-compose service.
  - Modified: `src/genex/db.nim` — extend `DatabaseConnection` with a small dialect descriptor (placeholder syntax, upsert clause, blob type) so the store layer can emit portable SQL.
  - New tests: `tests/test_db_store.nim` (SQLite-backed) and an integration suite under `testsuite/15-serialization/` exercising round-trip of every persistable `Vk*` kind.
- **Non-goals (deferred)**: secondary indexes on Gene properties, multi-row transactions across `put` calls, distributed/sharded layouts, compact binary wire format, migration tooling from filesystem-tier stores, **size-based auto-detach of root values into a content-addressed sidecar**, **the `^external_uri` "pre-uploaded blob" tier**, and **auto-detection of large leaf `VkString`/`VkBytes`/`VkBin` fields**. The first two are intentionally absent from v1; the third is a planned v2 follow-up that requires only schema additions (a `gene_values.blob_sha256` column) and reuses the v1 `gene_blobs`+`gene_value_blobs`+`VkLazyDbValue` machinery unchanged.
- **Deferred expansion: 1-n collection persistence**: v1 is intentionally a 1-1 root store (`id -> value`). A future change may add a collection/table mode for 1-n persistence, but it should be specified as a distinct API surface rather than a loose per-call boolean. The later spec should define collection identity (`store + collection_name`), record identity (`record_id` generated or caller-supplied), and explicit operations such as `open_collection`, `insert`, `update`, `delete`, `load_all`, and `query`. It should preserve the root-level CRUD rule: `insert` creates a record, `update` replaces one root record by id, `delete` removes one record by id, `load_all` materializes or lazily returns every record in a collection, and `query` returns records through declared queryable metadata/indexes. Arbitrary nested Gene-value predicates and child-path mutation/delete should remain out of scope unless the follow-up change also specifies declared indexes, query grammar, result ordering, pagination, and transactional semantics.
